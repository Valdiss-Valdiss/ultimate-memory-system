# Decisions.md — журнал архитектурных решений

> Формат записи: решение / почему / отвергнутые альтернативы.
> Заполняется агентом по мере работы. Версии инстансов — сверху.

## 2026-10-21 — Блок автономности: paramiko-транспорт, guard «Obsidian открыт», healthcheck CouchDB, netguard 30/60с, канари + авто-whitelist
- **Решение 1 (транспорт)**: ПК→VPS для бэкфиллов переведён на одно постоянное
  соединение (paramiko, keepalive, ретраи) вместо 5–6 новых SSH-соединений на файл.
  Почему: rate-limit на порт 22 (9 новых/60с) отбрасывал собственные служебные
  подключения; при «banner storm» ретраи сами себя поджигали.
  Отвергнуто: ControlMaster (Windows его не поддерживает), повышение порога
  как единственная мера (не убирает пачку соединений).
- **Решение 2 (guard)**: общий модуль `vault_guard.py`; все скрипты, пишущие в
  vault, проверяют, что Obsidian открыт, ДО любых действий. Курсор Telegram при
  этом не двигается. Отвергнуто: «открывать Obsidian из скрипта» (непредсказуемо
  для пользователя), «ждать синк» (гонка с плагином).
- **Решение 3 (healthcheck)**: «200 или 401 = жив» вместо `curl -f /_up`.
  Почему: 401 = контейнер жив, но docker видел «unhealthy» → внешний autoheal
  (у хостера) перезапускал CouchDB → обрывы синка у клиентов.
  Отвергнуто: healthcheck с кредями (секрет в описании контейнера).
- **Решение 4 (netguard)**: порог 30 новых соединений/60 с; логика вынесена в
  отдельный идемпотентный скрипт. Почему: рабочая машина может ходить через VPN
  с разными выходными IP, и жёсткий порог ловил собственные подключения.
  Парольная аутентификация отключена → риск от взлома не растёт.
- **Решение 5 (авто-whitelist + канари)**: ПК публикует свой публичный IP в
  заметку `Inbox/AI/Status/health.md`; серверный cron */10 добавляет ACCEPT-правило
  (TTL 7 дней, максимум 5 адресов). Отвергнуто: белый список «на все VPN-выходы»
  (неперечислимо), туннель до сервера (конфликтует с коммерческим VPN).
- **Решение 6 (интервал LiveSync)**: периодическая репликация 60 с → 300 с.
  Почему: при коротком интервале новый цикл мог вытеснить недозавершённый
  предыдущий — бэклог не догонялся никогда.
- **Решение 7 (мелочи конвейера)**: нейтральные маркеры вместо терминальных
  (частично обработанные альбомы больше не выпадают из обработки и не выглядят
  «необработанными»); в формулы `known` у обоих сканеров включён взаимный учёт
  маркеров; лимит загрузки документов и таймаут скачивания подняты (крупные
  книги и сканы); добавлена догенерация пустых медиа-резюме по тексту поста.


## 2026-09-21 — SSH-шум: rate-limit через iptables-контейнер вместо fail2ban
- **Решение**: лимит новых SSH-подключений (9/60с per-IP) правилами iptables в INPUT
  перед ufw + персистентный контейнер netguard_ssh22 (restart=always).
- **Почему**: fail2ban требует root; ControlMaster-мультиплексирование невозможен на
  Windows; смена порта сломала бы все проекты на 22-м порту.
- **Отвергнутые**: apt install fail2ban (нет root); порт 2222 (разъезд по клиентам);
  ControlMaster (Win32-OpenSSH не поддерживает — подключения падают).

## 2026-09-19/20 — Telegram 429: страж охлаждения в коде
- **Решение**: tg_floodguard.py — файл-маркер охлаждения; все скрипты с Telegram-сессией
  при старте проверяют маркер, при flood ставят 60 мин и выходят чисто.
- **Почему**: ретраи при 429 продлевают блок; ручной протокол не соблюдается в 3 ночи.
- **Отвергнутые**: бесконечные ретраи telethon (петля на 6345 строк); полная пауза
  всей задачи (бэкфиллы полезны и без Telegram).

## 2026-09-16 — Порядок CLI-цикла: mirror-last
- **Решение**: цикл = sync(in) → sync(out) → mirror (последний).
- **Почему**: mirror-шаг с newer-wins отклоняет ошибочные deletion-флаги и
  восстанавливает зеркало; волны удалений превращаются в самооткат.
- **Отвергнутые**: удаление outbound-шага (сломал бы поток бот→устройства); gate-затычки
  (блокировали легитимное воскрешение).

## 2026-09-24 — Лаунчеры фоновых процессов: Start-Process вместо wscript
- **Решение**: guard запускает python напрямую (Start-Process, stderr → файл).
- **Почему**: wscript молча умирает в Modern Standby-сессии; print в сломанный stdout
  убивал процесс (OSError 22) — log() теперь с try/except во всех скриптах.
- **Отвергнутые**: vbs-лаунчеры (интермиттентные смерти); stdout в NUL (потеря traceback).

## 2026-09-23 — Пропуск необрабатываемых хвостов
- **Решение**: терминальный маркер «не обработан» в заметке выводит цель из очереди
  навсегда (сканер SKIP_SIGNALS).
- **Почему**: таймауты скачивания больших медиа съедали часы; юзер принял частичную
  обработку ради скорости.
- **Отвергнутые**: бесконечные ретраи; ручное удаление заметок (потеря поста).

## 2026-09-16 — Дедупликация rename-дублей через CLI rm
- **Решение**: удалять воскрешённые старые имена через CLI `rm` по одному пути
  (ретраи между циклами), после проверки пар по (channel_id, msg_id) и контента.
- **Почему**: детерминированное удаление в БД; полный круг проверен тестом; не зависит
  от настроек плагина; не занимает Telegram-клиент.
- **Отвергнутые**: unlink на ПК (семантика внешних удалений неопределённа); ожидание
  самосходимости (newer-wins держит старые имена бесконечно).

## 2026-09-22 — Питание ноутбука: unattended sleep = 0
- **Решение**: powercfg UNATTENDSLEEP=0 (AC/DC) + STANDBYIDLE=0 + ноутбук в розетку.
- **Почему**: планировщик будил ПК на задачу → 2 мин тишины → standby → сеть подвешена
  → ночные конвейеры умирали.
- **Отвергнутые**: только таймер сна без unattended (не спасает); «пусть спит» (конвейеры
  падают каждую ночь).

## 2026-09-24 — Подготовка швов под графовый слой (neo4j)
- **Решение**: в docker-compose.yml заранее заготовлен закомментированный сервис
  neo4j (имя `neo4j`, сеть memnet, volume neo4j-data, heap 512–1024 MB,
  NEO4J_PASSWORD место в .env). В документации зафиксирован контракт: bolt внутри
  сети, имя хоста, бюджет RAM.
- **Почему**: включение следующей версии = раскомментировать + переменная окружения,
  без правки конфигов компонентов; RAM-планировка (12 GB рекомендовано) учитывает
  будущее потребление.
- **Отвергнутые**: отдельная ВМ под neo4j (лишний хостинг, сшивка сложнее);
  встраивание графа в Qdrant (разные роли: вектор vs связи).
- **Статус**: не внедрено — план следующей версии после публикации на GitHub.

## 2026-09-24 — selfhost-ai (kossakovsky): сценарий реюза, не основной установщик
- **Решение**: официальный путь установки Memory System — только наш compose
  (самодостаточный). Для серверов, где уже стоит selfhost-ai, документирован
  «Сценарий B»: реюз qdrant/docling/neo4j/Caddy через external network, ядро
  (couchdb/tei/tgapi/боты/indexer/netguard) — только из нашего compose.
- **Почему**: selfhost-ai не содержит couchdb/tei/tgapi (ядро!) — он физически не
  может установить Memory System; mixing двух источников правды (их make update
  ресетит tracked-файлы, у них свои имена/сеть/секреты) запутал бы и агентов, и юзеров.
- **Отвергнутые**: рекомендовать selfhost-ai как основной установщик (не ставит ядро);
  запрет на использование selfhost-ai вовсе (реюз общих сервисов — легитимный сценарий,
  именно так устроен продовый инстанс автора).
- **Neo4j**: разрешены оба источника (их селектор или наш закомментированный сервис) —
  но выбирается ровно один, имена хостов/креды не должны смешиваться.
