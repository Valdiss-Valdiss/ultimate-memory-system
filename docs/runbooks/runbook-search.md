# Runbook — поиск по памяти: как устроен, как настраивать, как проверять правки

## Как устроен (v0.2.0)

```
запрос пользователя ──┬─► как есть ───────────────┐
                      └─► расширение (дешёвая LLM) ┤   2 формулировки
                                                   ▼
                      смысловой индекс (e5, Qdrant)   словесный индекс (BM25, Qdrant)
                                                   ▼   4 списка
                                   слияние по местам (RRF, k=60) → до 100 заметок
                                                   ▼
                 find_notes: 20 лучших + описание 2–4 строки + 2 ссылки; заметка поиска с полным списком
```

- **Смысловой индекс** (`memory_indexer`): заметка режется на куски ~1300 символов (≈512 токенов —
  предел модели e5). Длинная расшифровка = десятки–сотни кусков, поэтому тема из конца интервью
  находится так же, как из начала. К каждому куску приклеен контекст:
  - кусок 0: `имя заметки. Канал: … Папка: … текст`;
  - куски 1+: `имя заметки. короткое описание заметки. текст`.
  Служебные поля frontmatter (тип, статус, id сообщения…) в текст НЕ попадают — они мешали смыслу.
- **Словесный индекс** (`bm25_indexer`): весь текст заметки, морфология ru/en (snowball), IDF считает Qdrant.
  Ловит точные слова, имена, названия сервисов, которые смысловой поиск размывает.
- **Расширение запроса** на сервере: одна дешёвая модель дописывает синонимы и английские
  эквиваленты. Одинаково для всех агентов (агентам запрещено «улучшать» запрос самим). Нет модели — поиск
  идёт без расширения.
- **Слияние RRF** складывает места заметки в четырёх списках (1/(60+место)) — устойчиво к разным шкалам оценок.
- **«Сначала свежее»** (`fresh=true`) — только по просьбе пользователя: 30 лучших пересортировываются по дате.

## Замеры автора (эталон 20–60 тем, nDCG@10 — качество первой десятки, 0…1)

| Что | Было → стало |
|---|---|
| Только смысловой, запрос «как есть» | 0,58 |
| + расширение запроса и BM25 (гибрид v0.2.0) | ≈0,71–0,74 |
| Индекс пересчитан без служебных полей: только смысловая часть | 0,525 → 0,665 (гибрид без изменений) |
| Замена e5 на BGE-M3 / Qwen3-Embedding-0.6B (60 тем) | +0,02…0,03 — в пределах погрешности |
| e5 + вторая модель параллельно (60 тем) | +0,04…0,05 (значимо), но ×2 память и CPU |

Не помогло: реранкер bge-reranker-v2-m3 (≈0 прибавки, медленный на CPU), постоянная надбавка за свежесть
(ухудшает), отсечка по порогу близости (не отличает нужное от ненужного), правило «искать строго по словам
пользователя» без расширения (−0,09). «Словесная» часть BGE-M3 слабее обычного BM25.

## Правило: любую правку поиска — сначала замер
Интуиция в поиске обманывает (см. последнюю строку выше). Порядок:
1. Собрать эталон (один раз): 40–60 тем — реальные запросы пользователя из заметок поиска
   (`Inbox/*/Search/`) + трудные (вопросы, перефразировки без общих слов, английские, поиск факта).
2. Для каждого варианта поиска сохранить первые 10–20 заметок по каждой теме.
3. Разметить объединённый пул (все варианты вместе): 2 — прямо по теме, 1 — частично, 0 — нет.
4. Посчитать nDCG@10, P@10 и **разницу с рабочим вариантом с 95% интервалом**:
   `tools/search-eval/eval_search.py` (формат файлов — в его README).
5. Внедрять, только если интервал разницы не пересекает ноль. На 20 темах погрешность ±0,06,
   на 60 — около ±0,03: 20 тем мало, чтобы поверить прибавке в 0,04.

Эталон содержит реальные запросы и названия заметок пользователя — он личный и в публичный
репозиторий не попадает.

## Пересчёт смыслового индекса
Нужен при смене формата кусков или модели. Индексатор пересчитывает только изменившиеся заметки;
для полного пересчёта — новая коллекция (`QDRANT_COLLECTION=<новое имя>`), отдельный state-файл
индексатора, переключение `mcp` на неё после замера; старую коллекцию держать для отката.
На CPU сервера (≈0,4 куска/с) 50 тыс. кусков — около 30 ч: можно посчитать на домашнем компьютере
той же моделью (режим bf16 почти не меняет векторы и в ~2 раза быстрее) и загрузить готовые векторы.

## Известные слабые места
- Тема, упомянутая в длинной заметке вскользь, проигрывает заметкам, целиком посвящённым теме
  (находится, но ниже первой десятки).
- Расширение запроса иногда возвращает мусор вместо формулировки — поиск не ломается, но теряет
  прибавку; при замене модели расширения проверяйте на эталоне.
- Если в vault просто нет заметок по теме, никакая модель не поможет — смотрите, что вообще сохраняется.
