# Runbook — Telegram-конвейер (бот + user-session)

## Два потока

1. **Бот (сервер, Bot API)**: вотчер следит за каналами → новые посты в staging →
   enrich (LLM/YT) → входная папка зеркала → CLI outbound → устройства.
   Быстро, без rate-limit юзера, но копии без полного обогащения.
2. **ПК (user-session)**: pc_catchup часами догоняет посты, скачивает вложения,
   делает OCR/транскрипты/резюме, раскладывает по целевым папкам.
   Медленнее (pacing), но полноценные заметки.

## Дисциплина: ОДИН клиент

Одновременные обращения к Telegram user-session из двух процессов →
`sqlite: database is locked` → падения. Правило:

- перед запуском бэкфилла проверить, что pc_catchup не запущен, и наоборот;
- в `pc_catchup.py` встроен yield: он уступает сессию бэкфиллу автоматически;
- часовая цепочка строго последовательная: catchup → triage → autorestart → renamer.

## Страж rate-limit (tg_floodguard.py)

- Файл-маркер `tg_cooldown_until.txt` (unix-время окончания охлаждения);
- Любой скрипт при старте: если охлаждение активно — мгновенный выход;
- При пойманном FloodWait/429 — охлаждение 60 мин и чистый выход (не ретраи!).
  Ретраи при 429 продлевают блокировку.
- Продлить охлаждение вручную: записать в маркер будущее unix-время.

## Папки каналов (folders.yaml)

- Автоматически ведётся pc_catchup (merge по ключам; ручные строки сохраняются);
- Новый канал: создать в Telegram, добавить бота админом, добавить строку в
  folders.yaml (`<имя канала>: "Целевая папка/"`);
- Фолбэк триажа: канал без маппинга → корневая папка по имени канала.

## Идемпотентность бэкфиллов

- Флаги frontmatter: `has_doc_text`, `has_ocr_text` — цель выходит из очереди;
- Guard по секциям: «строка проверки = строке записи» (дубли исключены);
- Терминальные статусы: «файл слишком большой», «не обработан (ошибка)»,
  «формат X не поддерживается», «текстовой нагрузки нет (мем)».
- Консервация хвоста: добавить в заметку маркер «не обработан» → цель навсегда
  выходит из очереди (использовать только по решению юзера).

## Прогресс и логи

- `attachments_backfill.log` — сводный; `photos_backfill.log` / `docs_backfill.log`
  — по фазам; `catchup.log` — часовая цепочка; `note_renamer.log` — переименования.
- Формат: `[+] N/total (note.md)` — счётчик очереди; `[skip]` — терминал; `[err]` — ретрай.
- stderr фоновых процессов всегда в файл (backfill_stderr.log) — traceback'и не теряются.

## Известные паттерны сбоев (проверенные фиксы)

| Симптом | Причина | Фикс |
|---|---|---|
| `sqlite3.OperationalError: database is locked` | два клиента одной сессии | yield/ожидание; запуск строго по одному |
| `Cannot send requests while disconnected` | сеть умерла (standby!) | см. runbook-windows-quirks.md; процесс перезапустит guard |
| `InvalidBufferError` / 429 петля | flood от Telegram | floodguard (уже встроен); не ретраить |
| Процесс «жив», но логи молчат часами | зависший download/print | stderr-файл покажет traceback; print защищён try/except |
| Заметки не появляются на ПК | Obsidian закрыт (guard запрещает внешние записи) | открыть Obsidian |
