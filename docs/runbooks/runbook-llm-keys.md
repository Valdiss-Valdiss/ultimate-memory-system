# Runbook - LLM-ключи: ротация, cooldown, истечение

> Ключи LLM (резюме, OCR-описания, переводы) могут истекать или упираться в
> окно лимита. Конвейер обязан продолжать работу, а не вставать молча.

## Как устроена ротация

`pc-scripts/yt_enrich.py` → `llm_call()`: кандидаты перебираются по порядку
(`LLM_KEY_1` → `LLM_KEY_2` → `LLM_KEY` → `auth.json` провайдера).

- **401/403** (ключ отозван/истёк) → ключ уходит в cooldown (по умолчанию 168 ч),
  работа продолжается на следующем кандидате.
- **429** (окно лимита исчерпано) → аналогично, но окно вернётся раньше.
- Сетевые ошибки/5xx → ключи перебираются без cooldown.

Состояние хранится локально в файле с **лейблами** (без значений ключей):
`pc-scripts/llm_key_cooldown.json`.

## Симптомы

- В отчёте канари: `LLM-ключ: КЛЮЧ ОТКАЗАН (LLM_KEY_1:401)`.
- Заметки приходят, но без резюме: `- **Резюме:** _(нет)_`.

## Что делать

1. Проверить живость ключей (1-токенный запрос, без полной генерации).
2. Получить новый ключ у провайдера и положить его в `.env`:
   `LLM_KEY_1=<новый>`, `LLM_KEY_2=<запасной>` (ПК и сервер — одинаково).
3. Сбросить cooldown-файлы (ПК: `pc-scripts/llm_key_cooldown.json`,
   сервер: `tg-bot/state/llm_key_cooldown.json`), иначе новый ключ не будет
   проверен до конца окна.
4. Перезапустить обогатитель на сервере (cron перезапустит сам).
5. Догенерация пропущенных резюме: `python pc-scripts/re_summary.py` (документы)
   и `python pc-scripts/media_re_summary.py` (медиа; если транскрипта нет —
   резюме строится по тексту поста).

## Профилактика

Проверяйте строку `LLM-ключ` в отчёте канари раз в сутки: она ловит
истечение ключа заранее, а не по факту «всё перестало переводиться».
