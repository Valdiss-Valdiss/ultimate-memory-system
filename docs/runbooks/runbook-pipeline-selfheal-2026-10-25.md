# Runbook: самовосстановление конвейера (2026-10-25)

> **Scope:** все механизмы авто-восстановления Memory System: триаж/догон на ПК, канарь, оповещения в чат бота Hermes, watchdog на VPS. Как работает, что проверять, что делать при отказе.
> Создан по решению юзера 25.10: «как только компьютер включается, подписка возобновляется, впн меняет статус — всё должно само восстанавливаться автоматически».

## Архитектура самовосстановления (слои)

| Слой | Что делает | Частота/условие |
|---|---|---|
| Задача «Memory Catchup Hourly» | догон постов → триаж → guard → renamer | каждые 60 мин; **StopExisting** (новый прогон убивает зависший); лимит 30 мин; **StartWhenAvailable** (пропущенный во сне прогон выстрелит при пробуждении); **триггер NetworkProfile 10000** (WiFi/VPN/сеть изменилась → немедленный прогон) |
| `pc_catchup.py` fail-fast | таймаут коннекта 120 с; сбор канала с таймаутом 480 с; убийство чужих инстансов на старте; flood-охлаждение через `tg_floodguard` | каждый прогон |
| Канарь (`health_canary.py`) | отчёт `Inbox/AI/Status/health.md` + строка в catchup.log; **авто-лечение**: pc_catchup старше 30 мин убивается | ежечасно в :37 |
| Ретранслятор (`/opt/memory-stack/prod/health_relay.py`, VPS) | читает health.md из зеркала; статус ≠ «в норме» → ⚠️ в чат бота Hermes; напоминание раз в 6 ч; «✅ восстановлено» при выздоровлении; канарь молчит ≥3 ч → предупреждение | cron */10 |
| Watchdog (`/opt/memory-stack/tg-bot/watchdog.sh`, VPS) | стоящие контейнеры tgapi/media → `docker start`; глухой вотчер tg_bot → рестарт | cron */10 |
| Whitelist-синк (`sync-whitelist.sh`) | ACCEPT текущего IP ПК (из заметки канаря) | cron */10 |
| LLM-ротация (`yt_enrich.py`) | 429/401/403 → cooldown 168 ч → следующий ключ; probe ключа №1 каждые 6 ч | в вызове |

## Что было сломано (инцидент 22–25.10) и почему

1. Прогон catchup 22.10 12:24 **завис** в Telethon (сетевой столл — известная нестабильность к Telegram DC). Коннект не имел таймаута.
2. Зависший процесс держал: (а) файл сессии SQLite → новые прогоны не могли открыть сессию; (б) хэндл catchup.log (наследованный от cmd `>>`) → маркеры новых прогонов не писались → «тишина» в логе.
3. Лаунчер-vbs выходил мгновенно → планировщик «успешно завершал» задачу за 1 сек (Result=0) → политики задачи никогда не срабатывали, зомби не замечался.
4. Во время зависания Telethon ушёл в reconnect-шторм: «wrong session ID» → Telegram затормозил сессию транспортным 429 → 1.66 млн строк мусора. Долбёжка заторможенной сессии продлевает бан — при флуде надо выходить, а не ретраить.
5. Долгоживущие python-дети guard'а наследуют эксклюзивный `>>`-хэндл cmd и запирают catchup.log на часы (механика инцидента 20.10). Лечение: guard → отдельный `guard.log`.

## Проверки здоровья (что смотреть)

- Заметка `Inbox/AI/Status/health.md` — «Статус: в норме» + свежесть «Telegram-догон» (<90 мин).
- Сообщения в чат бота Hermes при проблемах/восстановлении.
- VPS: `tail /opt/memory-stack/tg-bot/logs/health_relay.log`, `watchdog.log`, `enrich.log`.

## Действия при отказе

| Симптом | Действие |
|---|---|
| Догон ПРОСРОЧЕН >2 ч в health.md | `schtasks /query /tn "Memory Catchup Hourly" /v` — статус задачи; проверить python-процессы (`Get-CimInstance Win32_Process`); зомби убьётся сам (StopExisting + канарь), иначе `taskkill` вручную |
| Сообщение в чат не приходит | VPS: `python3 /opt/memory-stack/prod/health_relay.py --test` (отправит тестовое); проверить `docker exec hermes sh -c 'grep -c TELEGRAM_BOT_TOKEN /opt/data/.env'` = 1 |
| Контейнер стоит, watchdog не поднимает | watchdog сносит/стартует не чаще 1 раза в час (защита от циклов); ручной `docker start memory_tgapi` |
| Сессия Telegram «wrong session ID»/флуд | НЕ долбить: следующая попытка только через охлаждение (10 мин такт задачи + floodguard); при повторе — mini-test протокол из `runbook-ops-2026-09-14.md` |
