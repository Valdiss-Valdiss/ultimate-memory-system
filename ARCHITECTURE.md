# ARCHITECTURE.md — архитектура Memory System

## Назначение

Личная база знаний, которая автоматически собирает посты из приватных Telegram-каналов
в Obsidian-vault с обогащением и семантическим поиском. Всё зашифровано end-to-end,
синхронизировано между устройствами, переживает сбои.

## Компоненты

### Серверная часть (VPS, Docker)

| Компонент | Роль |
|---|---|
| `tg_bot` (watcher) | Следит за каналами Telegram (Bot API), складывает новые посты в staging |
| `tg_media` | Загружает медиа-вложения (фото/видео/документы) в кэш |
| `tgapi` | Локальный Telegram Bot API сервер (ускоряет загрузку медиа) |
| `enrich` | Обогащает заметки: LLM-резюме, транскрипты YouTube (TranscriptAPI → youtube-transcript-api → Deepgram фолбэк) |
| `CouchDB` | Единая синхронизационная БД для LiveSync (все устройства) |
| `CLI-цикл (reconcile)` | Каждые 30 с: `sync(in) → sync(out) → mirror (ПОСЛЕДНИЙ)` — зеркало с защитой newer-wins |
| `зеркало vault` | Расшифрованная текстовая копия vault на сервере (для индексатора и ИИ-ассистента) |
| `indexer` | Семантический индекс зеркала → Qdrant (чанки ~1300 симв., эмбеддинги через TEI) |
| `TEI` | Локальный сервер эмбеддингов (text-embeddings-inference) |
| `Qdrant` | Векторная БД для semantic_search |
| `docling` | Конвертер документов (PDF/DOCX → текст, OCR) |
| `ai-assistant` | ИИ-ассистент, работающий поверх заметок |
| `watchdog` | Авторестарт глухого бота (проверка offset раз в 10 мин) |

### Клиентская часть (ПК, Windows/Linux/macOS)

| Компонент | Роль |
|---|---|
| `Obsidian + LiveSync` | Vault, E2E-шифрование, синк на все устройства |
| `pc_catchup.py` | Часовой «догон» постов, пропущенных ботом (юзер-сессия Telegram) |
| `attachments_backfill.py` | Бэкфилл вложений: документы (docling+LLM) + фото (mimo-описания), идемпотентно |
| `triage_folders.py` | Раскладка заметок из входной папки в целевые по frontmatter `folder` |
| `note_renamer.py` | Переименование заметок с авто-именами в осмысленные (по OCR/резюме) |
| `tg_floodguard.py` | Страж rate-limit Telegram: маркер охлаждения, мгновенный выход при 429 |
| `catchup.bat` / cron | Часовая цепочка: pc_catchup → triage → autorestart → renamer |

### Потоки данных

```
[Пост в канале]
   ├── БОТ (VPS): watcher → staging → enrich → зеркало → CLI outbound → CouchDB → устройства
   └── ПК (user-session): pc_catchup (догон пропущенных) → vault-папка входа → triage → целевая папка

[Фото/видео/документы]
   └── tg_media (VPS) качает → заметка-стаб «смотрите по ссылке» →
       ПК бэкфилл: докачивает вложение → OCR/конвертация → секция «Изображение/Документ» в заметке

[Синк]
   └── Obsidian LiveSync (E2E) ↔ CouchDB ↔ CLI-цикл ↔ зеркало (self-healing, mirror-last)
```

## Целевое состояние (то, что проверяют validate-скрипты)

### Сервер (`validate/validate_vps.py`)

1. Docker активен; контейнеры стека `Up` без рестартов за последние часы;
2. CouchDB: `doc_count` > 0, `doc_del_count` == 0 (или объяснимо мал);
3. CLI-цикл: systemd-сервис active, последний цикл без ошибок;
4. Зеркало: число .md ≈ числу заметок vault'а, папки обновлялись недавно;
5. Indexer: циклы проходят, ошибки отсутствуют;
6. Watchdog-лог: без аномальных рестартов;
7. Диск < 80%, load < ядер×2.

### ПК (`validate/validate_pc.py`)

1. Obsidian запущен (для внешних записей в vault);
2. Планировщик: часовая задача активна;
3. Floodguard: маркер охлаждения отсутствует/истёк;
4. Один Telegram-клиент (не более одного процесса с сессией);
5. Питание: сон отключён (см. runbook-windows-quirks.md) — иначе бэкфиллы падают;
6. Vault: доступен, число .md согласовано с сервером.

## Запланированное расширение: графовый слой (neo4j)

Следующая версия репозитория добавит графовую базу знаний поверх заметок
(заметки/викилинки/бэклинки/теги/структура папок → граф). Чтобы апдейт был
бесшовным, в конфигурации уже зарезервированы «швы»:

1. **Сервис `neo4j`** заготовлен закомментированным в `vps/docker-compose.yml`
   (включение = раскомментировать + `NEO4J_PASSWORD` в `.env`);
2. **Имя хоста** в сети стека зарезервировано: `neo4j` (bolt://neo4j:7687) —
   будущие компоненты ходят по нему без правки конфигов;
3. **Volume** `neo4j-data` зарезервирован;
4. **Бюджет RAM**: рекомендованные 12+ GB уже учитывают ~1–1.5 GiB под neo4j
   (таблица — vps/README.md);
5. **Порты**: bolt только внутри сети; web (7474) — через реверс-прокси.

Планируемые роли графа: семантическая навигация по связям заметок, запросы
«что связано с X», обнаружение кластеров тем; доступ ИИ-агента — через MCP/bolt.

## Ключевые архитектурные решения (почему так)

Полный журнал — `docs/decisions.md`. Критичные:

1. **Mirror-last в CLI-цикле** — зеркальный шаг выполняется последним и защищает
   зеркало от ошибочных deletion-волн (самовосстановление). Порядок менять нельзя.
2. **E2E-шифрование LiveSync** — сервер не умеет читать vault; расшифровка — только
   на устройствах пользователя. Зеркало — сознательное исключение (нужно индексатору).
3. **Один Telegram-клиент** — sqlite-сессия не переносит параллельный доступ.
4. **Floodguard** — 429 лечится охлаждением, а не ретраями (ретраи продлевают бан).
5. **Идемпотентный бэкфилл** — флаги frontmatter (`has_doc_text`, `has_ocr_text`)
   и guard по секциям; повторный запуск не дублирует.

## Слои защиты (уроки аварий)

1. Mirror-last self-healing (сервер сам откатывает deletion-волны);
2. Deletion Propagation → корзина в Obsidian;
3. Снапшоты ВМ перед массовыми операциями + Duplicati/cron бэкапы ПК;
4. Floodguard (429) и netguard (SSH rate-limit);
5. Перехват stderr у всех фоновых процессов (никаких «молчаливых смертей»).
