# ARCHITECTURE.md — архитектура Memory System

## Назначение

Личная база знаний, которая автоматически собирает посты из приватных Telegram-каналов
в Obsidian-vault с обогащением, и даёт ИИ-агентам пользователя память — гибридный поиск по заметкам. Всё зашифровано end-to-end,
синхронизировано между устройствами, переживает сбои.

## Компоненты

### Серверная часть (VPS, Docker)

| Компонент | Роль |
|---|---|
| `tg_bot` (watcher) | Следит за каналами Telegram (Bot API), складывает новые посты в staging |
| `tg_media` | Загружает медиа-вложения (фото/видео/документы) в кэш |
| `tgapi` | Локальный Telegram Bot API сервер (ускоряет загрузку медиа) |
| `enrich` | Обогащает заметки: LLM-резюме, транскрипты YouTube (TranscriptAPI → youtube-transcript-api → Deepgram фолбэк) |
| `CouchDB` | Единая синхронизационная БД для LiveSync (все устройства) |
| `CLI-цикл (reconcile)` | Каждые 30 с: `sync(in) → sync(out) → mirror (ПОСЛЕДНИЙ)` — зеркало с защитой newer-wins |
| `зеркало vault` | Расшифрованная текстовая копия vault на сервере (для индексатора и ИИ-ассистента) |
| `indexer` | Смысловой индекс зеркала → Qdrant (куски ~1300 симв. с названием и описанием заметки, без служебных полей; эмбеддинги через TEI) |
| `bm25` | Словесный индекс (BM25, морфология ru/en) → Qdrant, заметка = точка |
| `memory-MCP` | Сервер памяти для ИИ-агентов: гибридный поиск, готовый ответ `find_notes`, «обобщи» (`search_digest`), чтение; запись — только в зону агента. Экземпляр на агента |
| `TEI` | Локальный сервер эмбеддингов (text-embeddings-inference) |
| `Qdrant` | Векторная БД: смысловая и словесная коллекции |
| `docling` | Конвертер документов (PDF/DOCX → текст, OCR) |
| агент в Telegram (опционально) | Например, Hermes: «найди / запомни / обобщи» из Telegram через свой экземпляр memory-MCP |
| `watchdog` | Авторестарт глухого бота (проверка offset раз в 10 мин) |

### Клиентская часть (ПК, Windows/Linux/macOS)

| Компонент | Роль |
|---|---|
| `Obsidian + LiveSync` | Vault, E2E-шифрование, синк на все устройства |
| `pc_catchup.py` | Часовой «догон» постов, пропущенных ботом (юзер-сессия Telegram) |
| `attachments_backfill.py` | Бэкфилл вложений: документы (docling+LLM) + фото (mimo-описания), идемпотентно |
| `triage_folders.py` | Раскладка заметок из входной папки в целевые по frontmatter `folder` |
| `note_renamer.py` | Переименование заметок с авто-именами в осмысленные (по OCR/резюме) |
| `tg_floodguard.py` | Страж rate-limit Telegram: маркер охлаждения, мгновенный выход при 429 |
| `catchup.bat` / cron | Часовая цепочка: pc_catchup → triage → autorestart → renamer |

### Потоки данных

```
[Пост в канале]
   ├── БОТ (VPS): watcher → staging → enrich → зеркало → CLI outbound → CouchDB → устройства
   └── ПК (user-session): pc_catchup (догон пропущенных) → vault-папка входа → triage → целевая папка

[Фото/видео/документы]
   └── tg_media (VPS) качает → заметка-стаб «смотрите по ссылке» →
       ПК бэкфилл: докачивает вложение → OCR/конвертация → секция «Изображение/Документ» в заметке

[Синк]
   └── Obsidian LiveSync (E2E) ↔ CouchDB ↔ CLI-цикл ↔ зеркало (self-healing, mirror-last)
```

## Память для ИИ-агентов (поиск)

```
агент (opencode / Claude / Hermes) ──HTTPS + токен──► Caddy ──► memory-MCP (зона Inbox/<агент>/)
                                                                   │
        запрос ──► как есть + расширение (дешёвая LLM, кэш) ──► смысловой (e5) + BM25
                                                                   │  4 списка → RRF (k=60)
        find_notes: 20 заметок + описание + [пост] · [открыть в Obsidian];  заметка поиска с полным списком
        «обобщи» → search_digest: отбор по теме → чтение целиком (сильная LLM) → сводка с номерами источников
```

- Агенты не «улучшают» запрос сами и не пересказывают ответ: расширение и формат — на сервере,
  поэтому все агенты отвечают одинаково, а правка делается в одном месте.
- Ссылки на источники формирует сервер: пост — только из сохранённого в заметке URL (не собирается из id),
  «открыть в Obsidian» — `obsidian://` и https-переходник для приложений, которые режут `obsidian://`.
- Служебные заметки (`Inbox/*/Search|Status|Trash/`) не индексируются и не являются источниками.
- Любая правка поиска — после замера на эталоне (`docs/runbooks/runbook-search.md`).
- Модель эмбеддингов одна для индексатора, сервера памяти и TEI; если TEI общий с другими проектами,
  модель в нём не меняется.

## Автономность и самовосстановление

Система спроектирована так, чтобы переживать сон ПК, обрыв сети, смену
IP-адреса (VPN) и тихие отказы внешних сервисов **без участия человека**.

| Механизм | Что делает | Где смотреть |
|---|---|---|
| `pc-scripts/vps_ssh.py` | Одно постоянное SSH-соединение (paramiko, keepalive) на весь прогон вместо 5–6 новых соединений на файл. Снимает rate-limit и «banner storm» | `pc-scripts/vps_ssh.py` |
| `pc-scripts/vault_guard.py` | Запрет записывать в vault при закрытом Obsidian (внешние правки при закрытом плагине приводили к волне удалений). Guard стоит **до** выборок: курсор Telegram не сдвигается, работа подхватится позже | `pc-scripts/vault_guard.py` |
| `pc-scripts/health_canary.py` | Раз в час проверяет всю цепочку (IP, SSH, LLM-ключ, CouchDB, очереди, свежесть логов, бэкапы) и пишет отчёт в заметку `Inbox/AI/Status/health.md` | `pc-scripts/health_canary.py` |
| `vps/scripts/sync-whitelist.sh` | По отчёту канари добавляет текущий публичный IP в SSH-whitelist (cron */10) — система переживает смену VPN-выхода | `vps/scripts/sync-whitelist.sh` |
| `vps/scripts/netguard-guard.sh` | Rate-limit SSH с идемпотентным набором правил (порог 30 новых соединений/60 с; парольная аутентификация отключена) | `vps/scripts/netguard-guard.sh` |
| Ротация LLM-ключей | Кандидаты ключей перебираются автоматически; 401/403 → cooldown, 429 → пауза. Ключи могут истекать — конвейер не должен вставать молча | `pc-scripts/yt_enrich.py` |
| Анти-зомби триаж | Задача: `StopExisting` (новый прогон убивает зависший) + лимит 30 мин + `StartWhenAvailable` (прогон, пропущенный во сне, стартует при пробуждении) + событие «сеть изменилась» → немедленный прогон. Лаунчер ждёт весь прогон — иначе политики задачи не действуют. Скрипт: таймаут коннекта 120 с, сбор канала 480 с, чужие инстансы убиваются на старте | `pc-scripts/catchup_hourly.*`, `pc-scripts/pc_catchup.py` |
| Канарь лечит | Прогон catchup старше 30 мин убивается. Ложные тревоги исключены: проблема = только «очередь > 0 И цепочка не подхватывала >1 ч»; простой и свежая цепочка = норма | `pc-scripts/health_canary.py` |
| Relay-оповещения | Проблема из health.md → сообщение в чат бота; напоминание раз в 6 ч; «восстановлено» при выздоровлении; ежедневный контрольный сигнал «штатная работа». Токен и chat_id читаются изнутри контейнера | `vps/scripts/health_relay.py` |
| Watchdog контейнеров | Стоящий контейнер (tgapi/media) → немедленный `docker start` (не чаще 1 раза в час на контейнер); глухой вотчер tg_bot остаётся | `vps/scripts/watchdog.sh` |
| Healthcheck CouchDB «200/401 = жив» | Старая проверка `curl -f /_up` давала 401 → контейнер числился unhealthy → внешние autoheal-механизмы его перезапускали, и синк рвался | `vps/docker-compose.yml` |
| Перезапуск с честным отчётом | Скрипты пишут причину отказа в лог (`[patch-skip]`, `[err]`, `[retry-later]`) — «молчаливых» пропусков больше нет | `pc-scripts/*.log` |
## Целевое состояние (то, что проверяют validate-скрипты)

### Сервер (`validate/validate_vps.py`)

1. Docker активен; контейнеры стека `Up` без рестартов за последние часы;
2. CouchDB: `doc_count` > 0, `doc_del_count` == 0 (или объяснимо мал);
3. CLI-цикл: systemd-сервис active, последний цикл без ошибок;
4. Зеркало: число .md ≈ числу заметок vault'а, папки обновлялись недавно;
5. Indexer: циклы проходят, ошибки отсутствуют;
5а. memory-MCP: `/health` = ok; коллекции смысловая и BM25 существуют и непусты; снаружи без токена — 401;
6. Watchdog-лог: без аномальных рестартов;
7. Диск < 80%, load < ядер×2.

### ПК (`validate/validate_pc.py`)

1. Obsidian запущен (для внешних записей в vault);
2. Планировщик: часовая задача активна;
3. Floodguard: маркер охлаждения отсутствует/истёк;
4. Один Telegram-клиент (не более одного процесса с сессией);
5. Питание: сон отключён (см. runbook-windows-quirks.md) — иначе бэкфиллы падают;
6. Vault: доступен, число .md согласовано с сервером.

## Запланированное расширение: графовый слой (neo4j)

Следующая версия репозитория добавит графовую базу знаний поверх заметок
(заметки/викилинки/бэклинки/теги/структура папок → граф). Чтобы апдейт был
бесшовным, в конфигурации уже зарезервированы «швы»:

1. **Сервис `neo4j`** заготовлен закомментированным в `vps/docker-compose.yml`
   (включение = раскомментировать + `NEO4J_PASSWORD` в `.env`);
2. **Имя хоста** в сети стека зарезервировано: `neo4j` (bolt://neo4j:7687) —
   будущие компоненты ходят по нему без правки конфигов;
3. **Volume** `neo4j-data` зарезервирован;
4. **Бюджет RAM**: рекомендованные 12+ GB уже учитывают ~1–1.5 GiB под neo4j
   (таблица — vps/README.md);
5. **Порты**: bolt только внутри сети; web (7474) — через реверс-прокси.

Планируемые роли графа: семантическая навигация по связям заметок, запросы
«что связано с X», обнаружение кластеров тем; доступ ИИ-агента — через MCP/bolt.

## Ключевые архитектурные решения (почему так)

Полный журнал — `docs/decisions.md`. Критичные:

1. **Mirror-last в CLI-цикле** — зеркальный шаг выполняется последним и защищает
   зеркало от ошибочных deletion-волн (самовосстановление). Порядок менять нельзя.
2. **E2E-шифрование LiveSync** — сервер не умеет читать vault; расшифровка — только
   на устройствах пользователя. Зеркало — сознательное исключение (нужно индексатору).
3. **Один Telegram-клиент** — sqlite-сессия не переносит параллельный доступ.
4. **Floodguard** — 429 лечится охлаждением, а не ретраями (ретраи продлевают бан).
5. **Идемпотентный бэкфилл** — флаги frontmatter (`has_doc_text`, `has_ocr_text`)
   и guard по секциям; повторный запуск не дублирует.
6. **Поиск собирает сервер, а не агент** — расширение запроса, слияние, ответ и ссылки; агент пересылает.
7. **Агент пишет только в свою зону** — экземпляр сервера памяти на агента; доступ снаружи — только с токеном.

## Слои защиты (уроки аварий)

1. Mirror-last self-healing (сервер сам откатывает deletion-волны);
2. Deletion Propagation → корзина в Obsidian;
3. Снапшоты ВМ перед массовыми операциями + Duplicati/cron бэкапы ПК;
4. Floodguard (429) и netguard (SSH rate-limit);
5. Перехват stderr у всех фоновых процессов (никаких «молчаливых смертей»).
