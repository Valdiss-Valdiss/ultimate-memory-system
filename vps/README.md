# vps/ — серверная часть Memory System

## Что здесь

| Файл/папка | Назначение |
|---|---|
| `docker-compose.yml` | Шаблон стека (все секреты через `.env`) |
| `.env.example` | Образец переменных — копировать в `.env` и заполнить |
| `scripts/` | Healthcheck, цикл reconcile, примеры systemd-юнитов |
| `bot/` | Исходники серверного конвейера (бот/watcher, enrich, медиа) |

## Требования к серверу (замерены на живом проде)

| Конфигурация | RAM | Комментарий |
|---|---|---|
| Минимум | **8 GB** | работает; при пиках конвертации docling тесно |
| **Рекомендуется** | **12 GB** | комфортно: пики конвертации + запас под будущий neo4j |
| Просторно | 16 GB | большой vault, крупные индексы, графовые аналитики |

Бюджет памяти компонентов (замер docker stats на проде, vault ~4–5 тыс. заметок):

| Компонент | Потребление |
|---|---|
| tei (модель эмбеддингов) | ~2.1 GiB |
| docling (конвертер) | ~1.2 GiB; **пики конвертации +1–3 GiB** |
| couchdb | ~90 MiB (растёт медленно с размером базы) |
| qdrant | ~70–300 MiB (растёт с числом векторов) |
| tg_bot + tg_media + tgapi | ~80 MiB суммарно |
| indexer | ~75 MiB |
| netguard | ~1 MiB |
| ОС + Docker | ~0.5–1 GiB |
| **Итого (штатно)** | **~4.5–5 GiB; пики ~7–8 GiB** |

CPU: 2 ядра минимум, 4 рекомендовано (tei/docling — тяжёлые).
Диск: 40 GB работоспособно, 80+ GB с запасом (медиа-кэш растёт).

### Запас под запланированный neo4j (графовый слой, следующая версия)

- Отдай компоненту ~1–1.5 GiB (heap 512–1024 MB для личных масштабов) —
  потому рекомендованная планка 12 GB уже учитывает его.
- Сервис уже **заготовлен закомментированным** в docker-compose.yml
  (включение = раскомментировать + добавить NEO4J_PASSWORD в .env).
- Имя хоста в сети стека зарезервировано: 
eo4j (по нему к нему ходить);

## Сценарий B: у тебя УЖЕ есть сервер на selfhost-ai (kossakovsky/selfhost-ai)

Memory System живёт рядом и **переиспользует** его общие сервисы — но ядро ставит
только наш compose (этих сервисов в selfhost-ai нет).

**Можно переиспользовать из selfhost-ai:**

- `qdrant` (их инстанс, вместо нашего),
- `docling`,
- `neo4j` (запланированный графовый слой: ВЫБОР ОДИН ИЗ ДВУХ — их или наш
  закомментированный сервис; оба поддерживаются, путать их нельзя),
- Caddy (HTTPS-фронт для couchdb/web-интерфейсов).

**Обязательно из нашего compose (в selfhost-ai отсутствуют):**

- `couchdb` (не входит в их набор!),
- `tei` (эмбеддинги), `tgapi`, `tg_bot`, `tg_media`, `indexer`, `netguard_ssh22` —
  это наш код и наш env-контракт.

**Как подключиться к их сети** (vps/docker-compose.override.yml, не коммитится):

```yaml
networks:
  memnet:
    external: true
    name: selfhost-ai_default
```

Тогда наши контейнеры ходят на их сервисы по именам (`qdrant:6333`, `docling:5001`).
Env индексера/конвейера выставить на их URL/ключи (брать из их `.env` — значения
не печатать в логи).

**Осторожно:**

- `make update` в selfhost-ai **ресетит tracked файлы** (docker-compose.yml/Caddyfile) —
  их кастомизации держать в docker-compose.override.yml и caddy-addon/;
- не публиковать их qdrant/neo4j наружу без авторизации (их дефолт — публичные URL);
- два инстанса qdrant (их + наш) на одном сервере — нормально, но выбери ОДИН для
  индексатора (env `QDRANT_URL`).

**Рекомендация по умолчанию:** сервер чистый → путь A (наш compose,
самодостаточный). Сценарий B — для тех, у кого selfhost-ai уже стоит, чтобы не
дублировать сервисы.

## Порядок развёртывания (кратко; полная версия — runbook-vps-setup.md)

1. Скопировать `vps/` на сервер (например, `/opt/memory-stack/vps/`).
2. `cp .env.example .env`, заполнить, `chmod 600 .env`.
3. `docker compose up -d` — стек поднимется.
4. Установить systemd-сервис CLI-цикла (см. `scripts/README-systemd.md`).
5. `python3 ../validate/validate_vps.py` — довести до зелёного.

## Автономность серверной части: healthcheck, netguard, канари

- **Healthcheck CouchDB** в `docker-compose.yml` возвращает «жив» и при коде
  401. Стандартная проверка `curl -f /_up` даёт 401 → docker считает контейнер
  умершим → внешний autoheal (у хостера) начинает его перезапускать, и синк
  рвётся у всех клиентов.
- **netguard** (`netguard_ssh22`): rate-limit SSH, 30 новых соединений/60 с,
  белый список IP. Логика вынесена в `scripts/netguard-guard.sh` (идемпотентна).
- **Авто-whitelist**: `scripts/sync-whitelist.sh` (cron */10) берёт текущий IP
  рабочей машины из отчёта канари (`Inbox/AI/Status/health.md` в зеркале) и
  добавляет ACCEPT-правило; старые адреса вычищаются (TTL 7 дней).
- **Канари на ПК** (`pc-scripts/health_canary.py`): проверяет SSH, ключи,
  CouchDB, очереди, бэкапы и пишет отчёт в заметку. Если канари молчит — ПК
  выключен или упала задача.
- **Ротация LLM-ключей** (на ПК и на сервере): кандидаты перебираются
  автоматически; 401/403 → cooldown, 429 → пауза. Подробности —
  `docs/runbooks/runbook-llm-keys.md`.


## Важно

- **`.env` никогда не коммитится.** Ключи Telegram/LLM хранятся только там.
- **E2E-парольная фраза vault не вводится на сервере** — только на устройствах.
- Зеркало vault (текстовая копия) создаётся CLI-циклом в каталоге, указанном
  в `MIRROR_DIR`.
- Контейнеры имён с префиксом проекта; общая docker-сеть для стека.

## Мини-стек vs полный стек

`docker-compose.yml` — минимально достаточный набор Memory System:
couchdb, qdrant, tei, docling, tgapi, tg_bot, tg_media, indexer, netguard.
Стек самодостаточен: перечисленные сервисы — всё, что нужно конвейеру памяти.
Другие сервисы (CMS, автоматизации и т.п.) не требуются и могут жить на соседних
инстансах независимо.
